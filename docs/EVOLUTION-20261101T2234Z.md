# cf-account-review — evolution plan

**Version:** 20261101T2234Z (previous: 20261101T2231Z, 20261101T2229Z, 20261101T2222Z, 20261101T2214Z) · **Covers:** v0.1 (first take, `6d5e46c`) → v0.2 (branch `web-security-v0.2`) → what comes next
**Focus:** the web security stack first; Zero Trust and platform checks follow the same model later.

This document reviews the first take, records what v0.2 changed and why, and lays out
how to evolve the tool. Decisions that are genuinely yours to make are collected in
[§7 Architecture questions](#7-architecture-questions). Implementation assumptions I made
without blocking are marked **Assumption**.

---

## 1. What the first take got right — keep these

- **Read-only by construction and by test.** GET-only client, GET-only shell wrappers,
  a test that fails on any mutating method or foreign host. This is the property that
  makes customers willing to run it. Do not trade it for any feature.
- **Fail-closed verdict semantics.** `pass | warn | fail | manual | na`, and "unreadable
  can never pass." The right contract for a review a customer will act on.
- **Two collection modes.** Offline Mode B (token never leaves the customer) is the
  mode security teams will actually approve.
- **Rulebook as data, citations on every check.** Peer-level credibility with a
  sophisticated customer comes from "here is the doc that says so," not from the tool.
- **Collection/analysis split with a versioned schema.** It is what makes offline mode,
  diffing, and a hosted analyzer possible.

Severity is about what the customer would have received, not code style. Mode B items
(#1, #2 bash/PS) were confirmed by running the original v0.1 collectors against the fake
API in `tests/fixtures/fake-api.json`; Mode A and analyzer items were confirmed by
reading the v0.1 code path and are pinned by v0.2 regression tests.

## 4. Design principles going forward

1. **Evidence before verdicts.** Every check declares the evidence it needs; the
   report shows coverage ("WAF: 11/12 checks had full evidence") so a reader can
   tell a clean report from a blind one.
2. **One definition of "what leaves the customer."** Today that is `summarize.ts`
   mirrored three times and held together by a parity test. The next step removes the
   mirroring (see §5.1).
3. **Context beats heuristics.** The tool cannot know that a zone has no login page
   or that `mail.example.com` is meant to be DNS-only. Give the customer a way to say
   so (§5.4) rather than tuning heuristics forever.
4. **Plan-aware, not plan-blind.** A Free zone's "fail" must be something the
   customer can fix on Free. Upsell signals belong in a separate section, never as fails.
5. **Remediation is generated, never applied.** Terraform/API snippets are output
   artifacts; the tool stays read-only.

## 5. Architecture direction

### 5.1 Collapse the three collectors

The parity test makes three implementations safe, not cheap: every new field is three
edits in three languages, and v0.1 shows how silently they diverge.

| Option | How | Pros | Cons |
|---|---|---|---|
| **A. Single binary** | Build `src/collect.ts` into a standalone executable (Node SEA or `bun build --compile`) for macOS/Linux/Windows; Mode B = "download, run, send JSON" | One implementation; customer needs no runtime; same redaction code everywhere | Unsigned binaries are a harder sell than a readable script; code-signing/notarization overhead |
| **B. Customer-side Worker** | Customer deploys a small Worker into *their* account (token as a secret), it writes the redacted collection to *their* R2 bucket; they download and send it | Cloudflare-native; no local runtime; token never leaves their account; easy to schedule for drift | Requires deploy permissions in the customer account (a write, even if not by this tool); larger trust ask |
| **C. Keep scripts, generate them** | Generate bash/PS summarizer code from one declarative spec of allowed fields | Keeps "read the script" auditability | Generator complexity; still three runtimes |
| **D. Status quo + parity test** | v0.2 | Works today | Ongoing 3× cost |

**Decided (2026-11-01): A — single binary. Requirement: the client installs no
runtime.** Implemented in `src/bin/collect.ts`, compiled with `bun build --compile`
for darwin-arm64/x64, linux-x64/arm64 and windows-x64 (Bun runtime embedded, ~90–115 MB
per file). It is the Mode A collector itself, so redaction, summarizers and the secret
scan exist once. Guarantees under test: same output as Mode A against the fake API;
the compiled binary runs with an empty `PATH`; the token prompt does not echo
(checked in a pseudo-terminal); a run that reads nothing exits non-zero and writes
nothing. CI builds all targets on every run and attaches them, with `SHA256SUMS`, to
the GitHub release on `v*` tags.

Decided follow-ups (2026-11-01):

- **No code signing.** Trust comes from the open source, published `SHA256SUMS`, the
  reproducible embedded bundle, and self-builds. Clients see Gatekeeper/SmartScreen on
  first run; the client guide explains it.
- **Scripts retired.** Both the PowerShell and the bash collectors are removed; the
  binary is the only Mode B collector, so collection, redaction and the secret scan
  exist exactly once. The parity test became `tests/collector-policy.test.ts` (planted
  secrets + evidence pinning against the fake API). The schema still accepts
  `collector: "powershell" | "bash"` so old collection files load.
- **Open source, inspect or self-build (decided 2026-11-01).** Auditability comes from
  the public source, not from shipping scripts. The JS bundle embedded in every binary
  is byte-for-byte reproducible and published with each release;
  `scripts/verify-build.sh` rebuilds it from a tag and compares hashes (CI runs it on
  every build). The executables themselves are not bit-identical across Bun builds
  (one trailer byte on Linux; macOS ad-hoc signing), so zero-trust clients build their
  own with `scripts/build-binaries.sh`. Bun is pinned exactly (1.4.4) for this reason.
- Bun was chosen over Node SEA because it cross-compiles every target from one Linux
  CI job; Node SEA needs a build per OS. Revisit if binary size matters (Bun's embedded
  runtime is the bulk of each file).

### 5.2 Rulebook model

Keep TypeScript evaluators for logic, but push structure into YAML:

- `requires:` — evidence paths a check needs; the engine produces `manual` with a
  precise reason before calling the evaluator (removes the per-evaluator boilerplate
  that caused #6).
- `planTier` per *verdict*, not per check (e.g., OWASP absent is a fail on
  Business+, a recommendation on Pro).
- `compliance:` tags (PCI DSS 4.0 6.4.1/6.4.3/11.6.1, SOC 2 CC6.6) — already on the
  TODO list; cheap once checks are stable.
- `fix:` — a parametrized remediation (dashboard path + API call + Terraform
  resource) for §5.5.

Rejected: Rego/CEL. They move logic out of TypeScript without removing it, and add a
runtime the customer may have to audit.

### 5.3 Hosted analyzer on Workers (Cloudflare-first)

The analyzer is pure TS with no Node-only dependencies beyond file I/O, so it can run
in a Worker:

- **Workers + Static Assets**: upload a collection, get the report (Markdown + HTML).
- **Access** in front for SE use; no customer data at rest by default (analyze in
  memory, return, discard).
- **Optional D1** for opt-in history → diff mode ("what changed since last quarter")
  and fleet views across an SE's accounts. Storing collections changes the data
  posture; make it explicit and opt-in.
- **Workers AI / AI Gateway** for an executive summary drafted *from findings only*
  (never from the raw collection), clearly labeled as generated.

### 5.4 Customer context file

`context.yaml` supplied with the collection (or kept by the SE per customer):

```yaml
zones:
  shop.example:
    loginPaths: ["/account/signin"]      # feeds CF-RL-001 instead of the heuristic
    expectedDnsOnly: ["mail.shop.example"]
    originLockdown: tunnel               # satisfies CF-AOP-001
accepted:
  - check: CF-WAF-004
    zone: legacy.shop.example
    reason: "OWASP false positives on legacy CMS; WAF exceptions planned"
    expires: 2027-03-31                  # expired acceptances become fails again
```

Accepted risks render in their own section with reason and expiry, never as passes.

### 5.5 Remediation output

Per failing check, emit the fix in three forms: dashboard path, API call (as a
commented `curl -X PATCH` the *customer* runs), and a Terraform resource. Output only;
nothing executes. This is the "future Terraform" already promised in CLIENT-GUIDE —
promise it per check once each check has a `fix:` block, not wholesale.

### 5.6 Output formats

Markdown (now) → HTML via the Worker (5.3) → JSON findings (machine-readable,
needed for diff and for CI `--fail-on`) → SARIF only if someone asks.

| Bot: JS detections enabled *and* acted on; static resource protection; AI-crawler policy reported (informational) | bot settings + rules | varies |
| Page Shield: policies (CSP) in enforce, not just monitoring | `/zones/{id}/page_shield/policies` | Enterprise |
| Origin CA / edge certificate coverage (wildcards vs hostnames actually proxied) | cert packs × DNS | any |

### P3 — breadth and polish

- Waiting Room presence on high-traffic paths (informational).
- Snippets / Workers in front of origin that may bypass rules (routing order).
- IP Lists used in allowlists (account lists referenced from skip rules).
- `security.txt`, HTTP/2 to origin, Opportunistic Encryption — low value, low cost.
- Upsell section ("available on your plan, not enabled" vs "requires upgrade").

## 7. Architecture questions

These change what gets built; I would like your call on each.

1. ~~**Mode B packaging (§5.1).**~~ **Decided: single binary, no client runtime.**
   Unsigned; PowerShell and bash collectors retired; source open with a reproducible
   embedded bundle and self-build path. Nothing left open here.
2. **Hosted analyzer (§5.3).** Should the analyzer run as a Worker behind Access for SE
   use, and if so, is storing collections (for diff/fleet views) in D1 in scope, or
   strictly analyze-and-discard?
3. **Who is the report for?** Today it is written for the customer's security team. An
   SE-facing variant (talk track, upsell signals, plan-gated opportunities) is a
   different document; keep them separate or one report with an SE appendix?
4. **Context file (§5.4).** Customer-authored, SE-authored, or both? This determines
   whether it ships with the collector or lives with the analyzer.
5. **Remediation output (§5.5).** Terraform resources, API calls, or both? Terraform
   only makes sense if your customers already manage Cloudflare with it.
6. **Scope beyond web security.** Next domain after web security: Zero Trust (Access
   policy depth, Gateway, device posture) or DNS/infrastructure (DNS firewall, Spectrum,
   Magic)? This decides the next profile.

## 8. Assumptions made in v0.2 (not blocking, but flagged)

- **Assumption:** zone plan names from the API include the tier word (e.g. "Enterprise
  Website"); `normalizePlan` prefers `plan.legacy_id` when present. Covered by tests
  for both shapes.
- **Assumption:** permission names in `src/endpoints.ts` for `ddos_l7` ("HTTP DDoS
  Managed Ruleset: Read"), `managed_headers` ("Transform Rules: Read"),
  `bot_management` ("Bot Management: Read"), and `/zones/{id}/rulesets`
  ("Zone Rulesets: Read", carried over from v0.1) match the dashboard. Reconcile during
  the token dogfood run; a wrong name only produces `manual` verdicts, never a false pass.
- **Assumption:** the publicly documented managed ruleset IDs in `KNOWN_MANAGED_RULESETS`
  are stable. They are a fallback only; the primary resolution uses the zone's own
  ruleset list (name → canonical key).
- **Assumption:** OWASP anomaly threshold above 60 is "too permissive" for CF-WAF-004
  (`maxScoreThreshold`, tunable in YAML).
- **Assumption:** country/ASN allowlists are always a `fail` (bypass of every security
  product for whole networks), IP/range allowlists a `warn`.
- **Assumption:** `CF-RL-001` login-path matching stays heuristic until the context file
  (§5.4) exists; the path list was extended (`/sign-in`, `/oauth/token`,
  `/wp-login.php`).
- Citation URLs added in v0.2 were not all fetchable from the build environment; CI's
  `scripts/check-citations.mjs` verifies every one on each push.
